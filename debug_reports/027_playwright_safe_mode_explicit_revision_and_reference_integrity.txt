3. 再現条件

保存済みCitationまたはVisual出力がPydantic shape検証を通過する一方、次のcross-artifact条件を満たさない場合に再現する。

- citation_required paragraphにCitationMappingがない。
- source/evidence locatorがmanifestにない。
- canonical limitationsの開示記録が不足する。
- Visual Cueが同じVisualPlan内に宣言されていないasset IDを参照する。
- Visual Cueが対象paragraphに存在しないevidence/source IDを追加する。

この状態で旧Safe Modeを使うと、修正可能性と自動再実行禁止が混同され、明示Revisionの入口が存在しなかった。

4. 根本原因

根本原因は三つの責務混在だった。

第一に、Safe Modeが「自動遷移を止める」という実行制御ではなく、Managerの設定済みrevision capacityそのものを0へ
書き換えていた。このため修正可能なREVISION_REQUIREDと修復不能なBLOCKEDを区別できなかった。

第二に、Providerへ渡すstrict schemaは型のshapeを保証していたが、現在のrequestに存在するsection/paragraph/evidence/
source/claim/asset ID集合まで拘束していなかった。LLMは構文上有効でも入力に存在しない参照を返せた。

第三に、limitations_to_discloseというManager所有のcanonical pass-through metadataをCitation LLMへ全文再転記させていた。
113件を一字一句再生成させる設計は、生成処理に不変metadataの完全コピー責務を負わせていた。

5. なぜこの問題が発生したか

Playwright初回実行の成功条件が、各Agent単体のPydantic validationと最終deterministic validationへ分離されていた一方、
その間にあるrequest-bound reference integrityをProvider response境界へ引き上げていなかった。
また、Conclusionで実装済みのSafe Mode明示一cycleという運用契約がPlaywrightへまだ一般化されていなかった。

6. なぜ既存テストで発見できなかったか

既存schemaテストは全object nodeのadditionalProperties=false、required完全一致、$defs/items/anyOf再帰を検証していたが、
request固有IDのenum化は対象外だった。Playwright recoveryテストもProvider failureからのcheckpoint復元を中心にしており、
決定論的gateが複数Agentを内部revision targetにした後のSafe Mode明示一cycleを扱っていなかった。
canonical limitation 113件とLLM返却3件の乖離、VisualPlan内のcue→asset自己参照もGolden Failureになっていなかった。

7. 修正計画

E2E Plan v2と照合し、次の順序で修正した。

1) 18 finding、PMP、state、reservation、artifact hashをFailure Captureする。
2) Safe Modeとrevision capacityの責務を分離する。
3) 明示的一回だけ保存findingを消費するPlaywright revision CLIを追加する。
4) Citation/Visualのrequest固有IDをstrict schema enumへspecializeする。
5) same-output cross-artifact invariantをPydantic modelへ追加する。
6) canonical disclosureをManagerで決定論的に保持する。
7) finding detailsとPrompt/RDを同じ契約へ揃える。
8) Static -> Unit -> Targeted -> Integration -> Mock -> Fault -> exact saved-state cloneを実行する。
9) productionへstorageを除外して反映し、Citation/VisualだけをOpenRouterへ各1回まで送る。

10. 修正の設計上の意味

Safe Modeの責務を「追加Provider call直前で自動遷移を停止すること」に限定し、Workflowが持つrevision capacityや
品質判断の意味を改変しないようにした。Operatorが明示した一回だけを新しいlogical taskとreservationで実行するため、
安全性、監査性、費用上限を同時に維持できる。

参照整合性は、汎用JSON Schemaのstrict化だけではなく、現在の入力集合に束縛されたrequest-specific schemaとlocal
cross-checkの二段防御にした。また、生成すべき文章とコピーすべきcanonical metadataを分離し、Manager所有の不変情報は
LLMに再生成させない。この設計によりStructured Outputを厳格化しても自由形式payloadの意味を破壊しない。
