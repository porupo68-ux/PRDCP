3. 再現条件

OpenRouter Structured Output要求は`response_format.type=json_schema`と`provider.require_parameters=true`を送る。
指定モデルについて、その必須パラメータを処理できるendpointが一つもない場合に404となる。
同一model/taskを再送してもrouting条件は変わらないため解決しない。

4. 根本原因

`require_parameters=true`は、Structured Outputsを無視するendpointへのroutingを防ぐ安全機構として正しく動作した。
根本原因はVisual Directorの設定モデルと必須Structured Output contractの能力不一致である。
一方、実装はこの特定404を汎用NonRetryableAgentErrorへ分類しており、次の三つを制御上区別できなかった。

- 一時障害なので同一モデルを一回retryするケース
- 応答本文が契約違反なので二回失敗後に別モデルへ修復するケース
- endpoint能力がないため最初の失敗直後に同一モデルを避けて別モデルへ移るケース

5. なぜこの問題が発生したか

Conclusionには応答契約違反用のdistinct-model repairがあったが、それは元callとoperator retryの二回が
ProviderResponseContractErrorになった場合だけを対象としていた。能力404は同一モデルretryが無意味であり、その前提に一致しない。
Playwrightには能力不一致専用authorization、model override、互換性bindingの利用経路がなかった。

6. なぜ既存テストで発見できなかったか

既存OpenRouter HTTP分類テストは404を他の非retryable statusと同じグループで検証していた。
Playwright recoveryテストは途中切断とPayload/contract failureを扱ったが、`require_parameters` routingが返す
endpoint能力404と、同一モデルを避ける必要性をFault Injectionしていなかった。

7. 修正計画

E2E Plan v2と照合し、次の順序を採用した。

1) exact Error PMP、reservation、state/checkpointを保存してFailure Capture。
2) OpenRouter公式Structured Outputs/Models仕様と照合。
3) Provider層で能力404を専用分類する。
4) 共通Base Agentに専用一回authorization/reservation enforcementを追加する。
5) Playwright Managerにcheckpoint-aware distinct-model recoveryを追加する。
6) 成功後だけprovider-Agent-output schema互換bindingを記録し、将来taskで再利用する。
7) Static -> Unit -> Targeted -> Integration -> Mock -> Fault -> exact saved-state clone。

10. 修正の設計上の意味

Provider failureを「もう一度試すか」だけで扱わず、「同じmodel contractで成功可能か」を実行制御へ昇格した。
能力不一致では安全機構を緩めず、元taskを再送せず、別task・別model・別reservationとして監査可能にする。
成功実績を広いmodel allowlistにせず、provider-Agent-output schema-configured modelの狭い契約として記録することで、
将来の同系統taskは同じ失敗を避けつつ、設定変更時に古いbindingが誤適用されない。
