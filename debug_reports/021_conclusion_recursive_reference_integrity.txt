2. 根本原因

JSON Schemaは文字列や配列の形を検証できるが、出力されたIDがDecision Contextのcanonical集合に
実在するかは検証できない。従来のConclusionValidatorはPositionのsupporting IDとIntegratorの
一部evidence参照だけを個別検査し、`related_claim_ids`のようなprefix付き参照、Evaluation、Package、
candidate/source/analysis/problem/stakeholder参照を一つの規則で再帰検証していなかった。

さらにAgentはPydantic validation後すぐsuccess PMP/Resultとして保存され、input-awareなdomain contractを
検証する共通境界がなかった。したがってschema-validだが存在しないIDがcheckpointへ確定し、後段Reviewer
だけが検出した。

保存済みDecision Context自体にも、tradeoffs内だけに存在しkey_claim_idsへ登録されていない次のlegacy参照が
あった。Integratorは入力に含まれるため、promptでallowlistを指示してもこれを複写できた。

- claim_observed_limited_displacement
- claim_perception_divergence
- claim_task_reorganization_observed

別の同系統不整合として、integrated_option.candidate_idsへcandidate IDだけでなく候補名と理由文が混入していた。

3. なぜ既存テストで発見できなかったか

既存テストはPydantic shape、候補のmatrix coverage、一部evidence参照、Reviewerのrouting整合を個別に確認していた。
任意のnested model、array、package複製を含め、明示的IDフィールドをcanonical集合と照合する横断テストがなかった。
またlegacy保存Decision Contextをそのまま複製したRecovery testが、provider-facing inputの不正参照まで含めていなかった。

4. 計画書との照合後に採用した修正計画

1) claim/evidence/analysis/source/candidate/stakeholder/problemの明示IDフィールドを再帰走査する。
2) 自由記述をIDとして誤検査せず、`*_id` / `*_ids`とviable_candidatesだけを対象にする。
3) Pydantic/schema validation後、success PMP/Result保存前にinput-aware contractを適用する。
4) Position、Evaluation、Integration、Packageの全artifactをdeterministic validationの同一集合で検査する。
5) legacy Decision Contextは保存JSONを変更せず、Provider送信用viewの明示IDフィールドだけを正規化する。
6) 保存済みReviewのtraceability findingはsaved artifactを再検証し、最初の不正生成段階へrevisionを絞る。
7) Safe Modeの明示revisionは設定された各slotを一回ずつ許し、上限超過はProvider call前に停止する。
8) automatic revision、PMP、Reservation、Outbox、Human Selectionは既存契約を維持する。

5. 実際の修正内容

- 共通StructuredAgentに、Pydantic後・success保存前の`validate_output_contract` hookを追加した。
- Conclusion Agentだけがhookをoverrideし、入力Decision Contextと出力IDの実在性を照合する。
- 違反時は正確なJSON pathを持つPayloadValidationErrorとなり、error PMPは保存するがsuccess Result、
  completed checkpoint、Quality Reviewer呼出しは作らない。
- ConclusionValidatorへ全artifact共通の再帰reference validatorを追加した。
- Decision Contextのprovider-facing copyで、未知IDを明示IDフィールドからだけ除去する。
  narrative、description、自由形式payload、および保存済みDeliberation Resultは変更しない。
- legacy trace-only ReviewはPosition → Evaluation → Integration → Packageの順に再検証し、
  最初に不正なartifactのproducerへrevision targetを絞る。
- 現workflowの有効targetはDecision Integratorだけとなる。依存関係によりQuality Reviewerだけが後続実行される。
- explicit revision上限を実行前に検査し、max_revisions=2ならrevision_1とrevision_2を各一回許す。
  3回目はReservation/Provider call前に停止する。automatic loopは変更していない。
- Evaluator/Integrator schema説明、Prompt、RDをcanonical ID allowlistに一致させた。

6. 修正の設計上の意味

Structured Outputの責務を「JSONとして正しい」から「そのworkflow入力に対して参照整合性がある」まで拡張した。
ただし共通hookの既定はno-opであり、Conclusionだけが明示的domain contractを実装するため、他Layerの既存挙動を
暗黙変更しない。LLMが作った不正参照を後段Reviewerへ委ねず、最初の生成境界で確定前に拒否できる。

provider-facing viewはlegacy保存物の非破壊compatibility adapterである。自由記述を削らず、明示ID配列だけを
canonical集合へ射影するため、意味のあるpayloadを機械的に破壊しない。

7. 同系統Failure Mode監査

- Position: candidate定義IDは自身の出力集合、context参照はDecision Context集合で検査する。

- Integration: candidate、tradeoff、profile、traceabilityのnested/array参照を再帰検査する。

- free text: `id`らしい語が文章に含まれても検査・削除しない。
- legacy context: 保存JSONを変更せずprovider viewだけ正規化する。
- revision routing: Reviewerの広いtargetをblindに採用せず、saved artifactで最初の不正producerを確定する。
- checkpoint: 完了済みPosition/Evaluationは再実行しない。
- reservation: revision_2 taskを新しいlogical taskとして一度だけ予約する。
- outbox: Human Selection完了前のConclusion/Playwright outboxは変更しない。
- 他Layer: 共通hookはdefault no-op。Producer/Researcher/Deliberation/Playwrightの実行契約は不変。
