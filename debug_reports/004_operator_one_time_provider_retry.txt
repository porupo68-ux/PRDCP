1. 何が起きたか

Cycle 003のOpenRouter Quality Reviewは、Structured Outputの生成途中にConnectionResetErrorで切断された。PRDCPはこれをRetryableAgentErrorとして正しく保存し、Demo Safe Modeにより自動retryを0回で停止した。一方、既存reservationを残したまま、運用者が同じcheckpointから一度だけ明示的に再送する安全な操作が存在しなかった。

2. なぜ起きたか

従来のSafe Mode reservationは「同一workflow・provider・logical taskの二重呼び出しを禁止する」責務だけを持っていた。外部Providerの一時障害後に、元の試行を消去せず、誰が・どのerrorに対して・何回目の再送を許可したかを永続化する制御面が未実装だった。通常の--researcher-resumeを再実行すると同じtask IDが選ばれ、既存reservationが安全に遮断するため、可用性と二重実行防止を両立する明示経路が必要だった。

4. どう直したか

common/provider_retry.pyにProviderRetryAuthorizationStoreを追加した。承認はworkflow、provider、agent、元task、元error messageを一意に結び、PENDINGからCONSUMEDへの一方向遷移だけを許可する。元reservationとretry reservationは両方保持する。

common/agents/base.pyの共通Provider境界は、_operator_retry_1 taskを受け取るとPENDING承認を要求する。新しいreservationを排他的に保存した後、Provider呼び出し前に承認をCONSUMEDへ遷移する。二つ目のプロセスは排他的reservationで遮断される。

Researcher Managerは現在のQuality Reviewer ERROR PMPと親TASK PMPを検証し、RetryableAgentErrorだけを承認する。再開時は承認済みretry taskを選び、保存済みReviewがあればProviderを呼ばず再利用する。CLIの--researcher-provider-retryはDemo Safe Mode ONを必須とする。

5. システム設計上の意味

reservationは「Providerへ送る意思を一度記録した」という事実、authorizationは「その失敗に対して運用者が一回だけ追加試行を許可した」という別の事実になった。障害復旧のために監査証跡を削除する必要がなくなり、安全性、可用性、追跡可能性を同時に維持できる。Provider呼び出し直前の共通境界で強制するため、将来ほかのLayerが同じ明示retry方式を採用してもLayer側の条件漏れだけで二重実行されない。

6. 同系統Failure Mode監査

- 同じ承認の再利用: CONSUMEDにより拒否。
- retryのretry: task suffix検査により拒否。
- 非Retryable error: error_class検査により拒否。
- 親requestが異なるerror: PMP message_id/parent_message_id/routing/task_id相関により拒否。
- provider namespace違い: 元reservationとprovider_id照合により拒否。
- 二プロセス同時実行: retry reservationの排他的作成により一方だけが進む。
- 承認保存後のプロセス中断: PENDING承認を再利用し、Manager再作成後もcheckpointから続行。
- reservation後・Provider前の中断: CONSUMEDかつreservation保持でFail Closed。同一callの重複可能性を作らない。
- Provider応答後・state保存前の中断: retry reservationを保持し、同じtaskの再送を禁止。保存済みReviewがある場合だけ再利用する。
