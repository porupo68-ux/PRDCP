1. 何が起きたか

Cycle 010の明示的一回Real Retryは64K context errorを解消し、OpenRouterからCounterargument JSONを受領した。しかしstrict response_format schemaにPydantic validatorの条件が表現されておらず、次の2件をlocal validationが拒否した。

- analysis_id=`counteranalysis_20260817_japan_ai_employment`。canonical prefix `counterargument_analysis_`ではない。
- `counter_polarization_1`はrequired_revision=falseだが、revision_target_agent_idsに`deliberation.researcher`を含めた。

同じrawでは、required_revision=trueの`counter_employment_impact_1`も`deliberation.researcher`を内部Agent targetとして含めていた。これは最初の2 validation errorには現れなかったが、Researcher routingと内部revision routingの責務混在である。

2. なぜ起きたか

Pydantic runtimeではanalysis_id field validatorとCounterargument model validatorが正しく拒否していた。一方、OpenRouterへ送ったJSON Schemaはanalysis_idを単なるminLength string、required_revisionをbool、revision_target_agent_idsを自由なstring arrayとして表現していた。

つまり「strict Structured Output schema」と「受信後Pydantic validation」が同じ契約を表していなかった。Providerは送信schemaには完全適合し得るJSONを返したが、ローカルの隠れた条件に失敗した。

3. 根本修正

- CounterargumentAnalysisResult.analysis_idへ`^counterargument_analysis_` patternを追加した。
- Primary 3分析のanalysis_id、Initial/Final integration_idにもcanonical patternを追加し、同系統を横断修正した。
- Counterargument itemをrequired_revision=true/falseの明示的Pydantic unionへ分割した。strict schemaではarray items以下にanyOfが生成される。
- true branchは内部Deliberation RevisionAgent enum、minItems=1、acceptance_conditions minItems=1。
- false branchはrevision_target_agent_ids maxItems=0。
- IntegrationRevisionのrevision_target_agent_idsも同じ内部Agent enumに限定した。
- Researcher追加調査は`research_gap_required=true`で表し、架空の`deliberation.researcher`をinternal targetとして許可しない。
- Counterargument prompt/RD/READMEへ同じ契約を明記した。

4. 保存rawの非破壊Recovery

7. 設計上の意味

Providerに見える契約と受信後validatorの契約を一致させた。直接JSON Schemaで表現できる条件を「promptで守る想定」のままにせず、anyOf/const/minItems/maxItems/enum/patternへ昇格した。一方、複数artifact間の参照整合のようなSchemaで表現困難な条件はlocal deterministic validationへ残し、責務を分離した。

保存rawを再利用することで、同じ論理Counterargument taskへの三度目のProvider callを発生させない。context repair reservationとinvalid rawを保持したまま、次のRecoveryはFinal Integrationから開始できる。
