1. 何が起きたか

Cycle 009修復後の実OpenRouter recoveryでは、Initial Integrationを保存checkpointからProvider call 0で復元できた。しかし次のCounterargument AnalystがHTTP 400を返した。OpenRouterの内容は「endpoint maximum context length 64,000 tokensに対し、text input約69,786 tokens」であり、自動retryは0、Final IntegrationとQuality ReviewのProvider callも0だった。

2. なぜ起きたか

直接原因はCounterargument payloadの過大化である。実保存データから再構成した送信候補は次の構成だった。

- system prompt: 18,001文字
- response_format schema: 6,298文字
- user input: 146,971文字
- user input中のResearch Report: 106,908文字
- user input中のInitial Integration: 29,422文字

Research Reportは、同じEvidence/Sourceの説明をsources、evidence_items、source_metadata、evidence_quality_assessmentsへ重複保持する正規化保存artifactである。保存形式としては正しいが、LLMへそのまま送ると同じ意味が最大4回入る。またagreements/conflicts/unresolved_itemsをInitial Integration内とCounterargument Task直下の両方へ送っていた。

同系統監査では、Final Integration候補が160,274文字、Quality Review候補が226,177文字だった。さらに全22 OpenRouter Structured Output rootで、同じstrict JSON Schemaをsystem promptへ全文埋め込みし、response_formatにも再送していた。Counterargumentだけを削る局所修正では、直後のManagerまたはReviewerで再発し得る設計だった。

3. Cycle計画とv2照合

計画:

1) 保存artifactとProvider実行viewを分離する。
2) Evidence、Source、Metadata、Qualityをtrace IDで一つの明示型recordへ統合し、意味・URL・引用・信頼度・source固有metadata・limitationsを保持する。
3) Initial Integrationに内包済みの配列をCounterargument Task直下から除く。
4) Final IntegrationはInitial IntegrationとCounterargumentを入力権威とし、full primary payloadを再送せずanalysis_id lineageだけを渡す。
5) Quality Reviewerには全履歴でなく、現行Researcher handoff、現行Primary task pair、現行Counterargument failure/repair、直近Review attemptからなる監査可能なPMP viewを渡す。全履歴はstorageに保持する。
6) strict schema本体はresponse_formatだけへ一度送る。schema検証・strict=true・全object additionalProperties=falseは維持する。
7) 既知のDeepSeek R1 64K上限を送信前に検査し、超過時はreservation作成前・HTTP前に停止する。
8) 保存済みcontext failureを検出した場合だけ、counter_task_revision_1_context_repair_1を一回限り使用する。元reservationは削除しない。
9) Deliberation Quality Reviewもrevision/recovery単位の決定的task identityにする。

v2照合結果:

- ResearchReport、state、message、checkpoint schemaは変更不要。実行時viewだけ追加可能。
- PMP保存形式は変更不要。Reviewer payload用trace selectorだけ縮約可能。
- Provider reservationはagent実行前に行われるため、budget preflightをBaseAgentとManager direct integrationのreservation直前へ置く必要がある。
- recover()は現在のrevision checkpoint選択を維持できる。resume()、Researcher Return、revision routingは変更不要。
- strict Structured Output変換は維持し、prompt内の重複コピーだけ除去できる。

- Manager、Counterargument、Quality ReviewerのPrompt/RDとREADMEへruntime view equivalenceを明記した。

5. 設計上の意味

Storage artifactは監査・再現のため完全で重複を含み得る。一方、Provider execution viewは、同じ意味を一度だけ表すbounded contextである。この二つを分離したことで、context節約のためにEvidenceや実行履歴を削除・書換えずに済む。

Schemaをpromptとresponse_formatへ二重送信することもやめたが、strict Structured Output安全機構は弱めていない。送信されるresponse_format schemaは従来どおり再帰検証済みで、全object nodeのadditionalProperties=falseとproperties==requiredを維持する。

Preflightをreservation前に置いたため、ローカルに確定できるoversize requestが「Providerを呼んでいないのに予約だけ消費する」状態も防止した。
